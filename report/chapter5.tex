\section{สรุปผลการดำเนินโครงงาน}
% -----------------------------------------------------------

การดำเนินโครงงานในระยะนี้ก้าวข้ามขั้นตอนการทดสอบเทคโนโลยีแกนหลักไปแล้ว โดยระบบทั้งเว็บแอปพลิเคชัน, ระบบหลังบ้าน, และ AI Service เชื่อมต่อและทำงานร่วมกันได้จริงแบบครบวงจรแล้ว ทั้งฟังก์ชันแชตบอตที่ตอบกลับแบบทยอยแสดงผล ฟังก์ชันสร้างและตรวจสอบคุณภาพแผนการเดินทางด้วยกลไก LLM-as-a-Judge อัตโนมัติ และฟังก์ชันเสริมด้าน AI อื่น ๆ เช่น การดึงข้อมูลกิจกรรมจากข้อความโพสต์ และการสร้างคำอธิบายสถานที่เฉพาะราย ส่วนของเว็บแอปพลิเคชันประกอบด้วยระบบบัญชีผู้ใช้ ระบบสแกน QR และแลกพอยท์ ระบบรายงานข้อมูล และระบบจัดการหลังบ้านที่เชื่อมต่อฐานข้อมูลจริงและนำขึ้นใช้งานบนเซิร์ฟเวอร์แล้ว ผลการประเมินความพึงพอใจด้วยแบบสอบถามจากผู้ใช้ \surveyN{} คนได้ค่าเฉลี่ยรวม \surveyOverallMean{} จาก 5 คะแนน อยู่ในระดับ\surveyOverallLevel{} (ตารางที่ \ref{tab:survey_items}) ทั้งนี้ยังมีงานที่ต้องดำเนินการต่อในด้านการทดสอบยอมรับจากผู้ใช้แบบกำหนดภารกิจและการขยายกลุ่มผู้ประเมิน

1. Backend และฐานข้อมูล & ฐานข้อมูล PostgreSQL (Supabase) 26 ตาราง พร้อม REST API ที่ตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ ระบบบัญชีผู้ใช้ด้วยเซสชันแบบ cookie และการยืนยันอีเมล ฟังก์ชันสแกน QR และแลกของรางวัลที่ทำงานในธุรกรรมเดียว บันทึกการดำเนินการของผู้ดูแลระบบ และการเพิกถอนสิทธิ์เขียนฐานข้อมูลของผู้ใช้สาธารณะ & ยังไม่มี Content Security Policy เต็มรูปแบบ การตรวจชนิดไฟล์อัปโหลดอาศัย mimetype จากฝั่งผู้ใช้ ไม่มีการล็อกบัญชีนอกจากการจำกัดอัตราคำขอ และฐานข้อมูลที่ใช้งานจริงไม่มีประวัติ migration จึงต้องนำไฟล์ใหม่ไปใช้ทีละไฟล์ \\ \hline
2. User Portal (ผู้ใช้งานทั่วไป) & หน้าหลัก, รายละเอียดสถานที่/กิจกรรม, ค้นหา, แชตบอต, สร้างแผนการเดินทาง, หน้าทริปของฉันสำหรับเปิดดูและจัดการแผนที่บันทึกไว้, หน้าพอยท์สะสมพร้อมสแกน QR ผ่านกล้อง, สมัครสมาชิก เข้าสู่ระบบ และตั้งรหัสผ่านใหม่, โปรไฟล์และรูปประจำตัว, แจ้งข้อมูลคลาดเคลื่อน, คำขอเพิ่มกิจกรรม และแบบสอบถามความพึงพอใจ ครบทุกหน้าจอ เชื่อมต่อ API จริง & ผลแบบสอบถามความพึงพอใจสรุปไว้ในบทที่ 4 แล้ว (ตารางที่ \ref{tab:survey_items}) แต่มีผู้ตอบเพียง \surveyN{} คน \\ \hline
3. Admin Portal (ผู้ดูแลระบบ) & จัดการข้อมูลสถานที่ กิจกรรม ฐานความรู้ QR/ของรางวัล แบบ CRUD พร้อมเครื่องมือช่วยดึงข้อมูลกิจกรรมจากโพสต์ด้วย AI, คิวตรวจสอบรายงานและคำขอกิจกรรม, นำเข้าและซิงก์ข้อมูลสถานที่จาก Google Places พร้อมล็อกรายฟิลด์, แลกของรางวัลที่เคาน์เตอร์พร้อมยกเลิกรายการ, บริหารบัญชีผู้ใช้และปรับพอยท์, สถิติระบบ และสรุปผลแบบสอบถาม เชื่อมฐานข้อมูลจริงและตรวจสิทธิ์ผู้ดูแลระบบที่ฝั่งเซิร์ฟเวอร์ & การซิงก์ข้อมูลสถานที่เริ่มได้เฉพาะเมื่อผู้ดูแลระบบสั่ง ยังไม่มีการซิงก์อัตโนมัติตามรอบเวลา \\ \hline
4. AI \& LLM Integration & RAG (Hybrid Search ผ่าน pgvector) ครอบคลุมสถานที่ ฐานความรู้ และกิจกรรม, แชตบอต Streaming ที่สนทนาต่อเนื่องหลายรอบได้, วางแผนทริปแบบผสม (LLM คัดเลือกสถานที่ ส่วน Scheduler เชิงกำหนดแน่นอนจัดลำดับและเวลา) พร้อม LLM-as-a-Judge, บันทึกแผนที่สร้างลงฐานข้อมูลโดยอัตโนมัติ (UC-07), ดึงข้อมูลกิจกรรมจากโพสต์ด้วย AI, ปุ่มสร้างคำอธิบายสถานที่ด้วย AI ในฟอร์มสถานที่, ปุ่มสร้างดัชนี Embedding ใหม่ใน Admin Portal และการบันทึกปริมาณ Token/ค่าใช้จ่ายต่อคำขอ เชื่อมเข้าระบบจริงครบแล้ว & การสร้างคำอธิบายสถานที่ด้วย AI ทำได้ทีละสถานที่จากฟอร์ม การสร้างทั้งตารางในคราวเดียวยังต้องรันสคริปต์แยกนอกระบบ; ค่าเกณฑ์ผ่านของ LLM-as-a-Judge (0.45) ยังไม่ได้ปรับเทียบกับโมเดลและเกณฑ์ชุดปัจจุบัน; ฟังก์ชันปรับแผนด้วยการกดถูกใจ/ไม่ถูกใจถูกถอดออกจากหน้าผู้ใช้ จึงยังไม่มีช่องทางให้ผู้ใช้ปรับแผนหรือส่งข้อเสนอแนะให้ LLM หลังสร้างแผนเสร็จ \\ \hline
5. Data Retrieval (ข้อมูลภายนอก) & Google Places API (ข้อมูลตั้งต้น) และ Serper API (ค้นข้อมูลเสริมสร้างคำอธิบายสถานที่) & สำเร็จครบตามที่ออกแบบไว้ \\ \hline
6. Testing \& Deployment & นำระบบทั้งสามส่วนขึ้นใช้งานจริงบนเซิร์ฟเวอร์เสมือนเครื่องเดียวด้วย Docker Compose และ Caddy พร้อมปรับปรุงอัตโนมัติผ่าน GitHub Actions; มีชุดทดสอบฝั่ง Backend ครอบคลุมหน้าสำหรับ SEO และแบบสอบถาม; มีชุดทดสอบอัตโนมัติสำหรับ Judge, Trip Planner และ Scheduler (Unit Test แบบ Mock คำตอบ LLM), ชุด Golden Set ที่เรียกโมเดลจริงสำหรับฟังก์ชันแชตบอต และชุดทดลองเปรียบเทียบ Prompt ของ Trip Planner ที่เรียกโมเดลจริง 96 รัน (ตารางที่ \ref{tab:prompt_eval}) ซึ่งผ่านตัวชี้วัด Environment/Hard/Commonsense ร้อยละ 100; และประเมินความพึงพอใจของผู้ใช้ \surveyN{} คนด้วยแบบสอบถามในระบบ (ตารางที่ \ref{tab:survey_items}) & การทดลอง Trip Planner ยังไม่รวมวงรอบสร้างแผนใหม่ของ Judge และยังไม่ได้เทียบผู้ประเมินกับคะแนนจากมนุษย์; ยังไม่ได้ประเมินแชตบอตตามตัวชี้วัด Answer Relevance, Faithfulness และ Context Recall/Precision; ยังไม่ได้ทดสอบยอมรับจากผู้ใช้แบบกำหนดภารกิจ (UAT) และกลุ่มผู้ตอบแบบสอบถามยังมีขนาดเล็ก \\
\hline
\end{longtable}

\subsection{ข้อจำกัดด้านการทำงาน}

แม้ระบบหลักจะเชื่อมต่อกันแบบครบวงจรแล้ว แต่ยังพบข้อจำกัดสำคัญในส่วนที่ยังไม่สมบูรณ์ ดังนี้

\begin{enumerate}[label=(\arabic*),leftmargin=0pt,itemindent=\dimexpr\parindent+\parenlabelwidth+1em\relax,align=right,labelwidth=\parenlabelwidth,labelsep=1em]
\needspace{5\baselineskip}
\item มาตรการด้านความปลอดภัยยังไม่ครบถ้วน แม้ระบบจะตรวจสอบการยืนยันตัวตนและสิทธิ์ที่ฝั่งเซิร์ฟเวอร์แล้ว แต่ยังไม่มีนโยบาย Content Security Policy เต็มรูปแบบ (กำหนดเพียง frame-ancestors) เนื่องจากหน้าเว็บโหลดสคริปต์และรูปภาพจาก Google Maps และ Cloudinary การตรวจชนิดไฟล์อัปโหลดอาศัย mimetype ที่ฝั่งผู้ใช้ส่งมา และยังไม่มีการล็อกบัญชีหลังเข้าสู่ระบบผิดซ้ำนอกเหนือจากการจำกัดอัตราคำขอ
\item การดูแลโครงสร้างฐานข้อมูลต้องดำเนินการด้วยตนเอง ฐานข้อมูลที่ใช้งานจริงไม่มีประวัติ migration ของ Supabase หากสั่งนำ migration ทั้งหมดไปใช้ซ้ำจะประมวลผลไฟล์เดิมทั้งหมดอีกครั้ง จึงต้องนำไฟล์ใหม่ไปใช้ทีละไฟล์ และสคริปต์ปรับปรุงระบบ (deploy.sh) ไม่ได้ดำเนินการส่วนนี้ให้
\item ข้อมูลสถานที่จาก Google ซิงก์ได้เมื่อผู้ดูแลระบบสั่งเท่านั้น ระบบยังไม่มีการซิงก์ตามรอบเวลา และแต่ละสถานที่ที่ซิงก์ต้องเรียก Google Places API ซึ่งมีค่าใช้จ่ายตามจำนวนครั้ง จึงจำกัดชุดงานละไม่เกิน 500 แห่ง
\item แผนการเดินทางปรับแก้ไม่ได้หลังสร้างเสร็จ ระบบบันทึกทุกแผนลงตาราง trips, trip\_days และ trip\_items โดยอัตโนมัติ และผู้ใช้ที่เข้าสู่ระบบเปิดดู เปลี่ยนชื่อ ทำสำเนา และลบแผนได้ (UC-07) แต่ฟังก์ชันปรับแผนด้วยการกดถูกใจ/ไม่ถูกใจและช่องข้อเสนอแนะที่เคยพัฒนาไว้ถูกถอดออกจากหน้าผู้ใช้แล้ว ผู้ใช้ที่ต้องการแผนต่างจากเดิมจึงต้องกรอกเงื่อนไขและสร้างแผนใหม่ทั้งชุด นอกจากนี้ แผนของผู้ที่ไม่ได้เข้าสู่ระบบถูกบันทึกเพื่อสถิติของผู้ดูแลระบบเท่านั้นและเปิดดูซ้ำไม่ได้ และบัญชีหนึ่งบันทึกแผนได้ไม่เกิน 50 แผน
\item ระยะทางและเวลาเดินทางในแผนเป็นค่าประมาณ ระบบคำนวณระยะทางแบบเส้นตรง (Haversine) และใช้ความเร็วเฉลี่ยคงที่ (25 กิโลเมตรต่อชั่วโมงในเขตเมือง และ 60 กิโลเมตรต่อชั่วโมงเมื่อระยะทางเกิน 15 กิโลเมตร) มิได้ใช้ข้อมูลเส้นทางหรือสภาพจราจรจริง เวลาในตารางจึงอาจคลาดเคลื่อนจากการเดินทางจริง
\end{enumerate}

\subsection{ข้อจำกัดด้านฮาร์ดแวร์และซอฟต์แวร์}

ระบบพึ่งพาการประมวลผลผ่านโมเดลภาษาขนาดใหญ่ตระกูล Gemini ที่เรียกผ่าน Vertex AI ของ Google Cloud ซึ่งกำหนดโควต้าอัตราคำขอต่อโครงการและคิดค่าใช้จ่ายตามปริมาณ Token ทำให้อาจเกิดการหยุดชะงักของบริการเมื่อคำขอเกินโควต้าหากมีผู้ใช้งานพร้อมกันจำนวนมาก และค่าใช้จ่ายเพิ่มขึ้นตามปริมาณการใช้งาน โดยช่วงวันที่ 10--15 ตุลาคม 2569 ซึ่งรวมช่วงเก็บแบบสอบถามความพึงพอใจ มีค่าใช้ Vertex AI รวม 135.24 บาท ซึ่งชำระด้วยเครดิตทดลองใช้ฟรีของ Google Cloud (ตารางที่ \ref{tab:cost}) เมื่อเครดิตหมดลงค่าใช้จ่ายส่วนนี้จะเป็นภาระของผู้ดูแลระบบโดยตรง นอกจากนี้ ค่าเกณฑ์ผ่านของกลไก LLM-as-a-Judge (0.45) ถูกปรับตั้งจากผลทดสอบกับโมเดลชุดแรกที่ใช้งาน (gemini-2.5-flash) เท่านั้น ปัจจุบันระบบเปลี่ยนมาใช้ gemini-3.8-flash และปรับขอบเขตเกณฑ์ของ Judge ให้แคบลงแล้ว แต่ค่าดังกล่าวยังไม่ได้ทดสอบและปรับเทียบใหม่

โควต้าของ LLM อาจหมดลงได้หากมีผู้ใช้งานพร้อมกันจำนวนมาก & ระบบพึ่งพาการประมวลผลผ่าน Gemini บน Vertex AI ซึ่งมีการกำหนดเกณฑ์การใช้งาน (Rate Limits) และคิดค่าใช้จ่ายตามปริมาณ Token & 1. แยกตัวแปรตั้งค่าโมเดลตามลักษณะงาน เพื่อให้เปลี่ยนโมเดลของงานใดงานหนึ่งได้โดยไม่กระทบงานอื่น และสลับผู้ให้บริการได้ด้วยตัวแปร LLM\_PROVIDER แม้ปัจจุบันทุกงานจะใช้ gemini-3.8-flash \newline 2. จำกัดจำนวนรอบการสร้างแผนซ้ำของ LLM-as-a-Judge ไว้ไม่เกินค่าที่กำหนด (MAX\_JUDGE\_ATTEMPTS) เพื่อไม่ให้คำขอเดียวใช้โควต้าเกินความจำเป็น \newline 3. ตั้งค่าให้ขั้นตอนตรวจสอบคุณภาพ (Judge) ทำงานแบบ Fail-Open หากเรียก API ไม่สำเร็จ เพื่อไม่ให้ปัญหาโควต้าที่ขั้นตอนตรวจสอบไปปิดกั้นผลลัพธ์หลักที่สร้างเสร็จแล้ว \newline 4. จำกัดจำนวนคำขอต่อผู้ใช้แต่ละราย (Rate Limiting) ที่ AI Service โดยค่าเริ่มต้นคือแชตบอต 20 ครั้งต่อนาทีและ 200 ครั้งต่อชั่วโมง ส่วนการวางแผนทริป 5 ครั้งต่อ 10 นาทีและ 20 ครั้งต่อชั่วโมง \newline 5. บันทึกปริมาณ Token และค่าใช้จ่ายโดยประมาณของแต่ละคำขอ เพื่อติดตามการใช้โควต้า \newline (แนวทาง Local LLM/Semantic Caching ที่เคยเสนอไว้ในรายงานฉบับก่อนหน้ายังไม่ได้นำมาใช้จริง) \\

\subsection{การปรับปรุงฟังก์ชันการทำงาน}

เพื่อให้ระบบมีความสมบูรณ์และพร้อมใช้งานจริงยิ่งขึ้น ควรเสริมมาตรการความปลอดภัยของเว็บแอปพลิเคชันที่ยังเปิดอยู่ ได้แก่ การกำหนด Content Security Policy การตรวจชนิดไฟล์อัปโหลดจากเนื้อไฟล์ และการล็อกบัญชีหลังเข้าสู่ระบบผิดซ้ำ ควรจัดให้ฐานข้อมูลที่ใช้งานจริงมีประวัติ migration เพื่อปรับปรุงโครงสร้างได้อัตโนมัติ และเพิ่มการซิงก์ข้อมูลสถานที่ตามรอบเวลา ควรพัฒนาช่องทางให้ผู้ใช้ปรับแผนการเดินทางหลังสร้างเสร็จ โดยส่งความเห็นของผู้ใช้กลับไปให้ระบบวางแผนประมวลผล นอกจากนี้ ควรศึกษาแนวทางการเข้าถึงข้อมูลความหนาแน่นของผู้คนจากแหล่งข้อมูลเปิดอื่นที่ยังไม่เคยทดลอง เพื่อเพิ่มประสิทธิภาพในการแนะนำแผนการเดินทางให้สอดคล้องกับสถานการณ์จริงยิ่งขึ้นและเมื่อฟังก์ชันหลักครบถ้วนสมบูรณ์ ควรทดสอบยอมรับจากผู้ใช้แบบกำหนดภารกิจ (UAT) และเก็บแบบสอบถามความพึงพอใจจากกลุ่มผู้ใช้ที่กว้างและหลากหลายกว่าเดิม เพื่อประเมินประสิทธิภาพและความพึงพอใจของผู้ใช้งาน รวมถึงปรับเทียบค่าเกณฑ์ผ่านของกลไก LLM-as-a-Judge ใหม่ให้ตรงกับโมเดลที่ใช้งานอยู่ ทดลองระบบวางแผนการเดินทางแบบรวมวงรอบสร้างแผนใหม่ของ Judge และประเมินแชตบอตตามตัวชี้วัด Answer Relevance, Faithfulness และ Context Recall/Precision ที่วางแผนไว้ ตลอดจนเปรียบเทียบโมเดลภาษาขนาดใหญ่หลายรุ่นในด้านความแม่นยำ ความเร็วในการตอบสนอง และต้นทุนการใช้งาน เพื่อเลือกโมเดลที่เหมาะสมกับแต่ละฟังก์ชัน (แชตบอต, Trip Planner, Judge) แทนการใช้ gemini-3.8-flash รุ่นเดียวกับทุกฟังก์ชันดังในปัจจุบัน
