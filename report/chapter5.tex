\section{ข้อจำกัดของระบบ}
% -----------------------------------------------------------

\subsection{ข้อจำกัดด้านการทำงาน}

ระบบมีข้อจำกัดด้านการทำงาน ดังนี้

\begin{enumerate}[label=(\arabic*),leftmargin=0pt,itemindent=\dimexpr\parindent+\parenlabelwidth+1em\relax,align=right,labelwidth=\parenlabelwidth,labelsep=1em]
\needspace{5\baselineskip}
\item มาตรการด้านความปลอดภัยยังไม่ครบถ้วน แม้ระบบจะตรวจสอบการยืนยันตัวตนและสิทธิ์ที่ฝั่งเซิร์ฟเวอร์แล้ว แต่ยังไม่มีนโยบาย Content Security Policy เต็มรูปแบบ (กำหนดเพียง frame-ancestors) เนื่องจากหน้าเว็บโหลดสคริปต์และรูปภาพจาก Google Maps และ Cloudinary การตรวจชนิดไฟล์อัปโหลดอาศัย mimetype ที่ฝั่งผู้ใช้ส่งมา และยังไม่มีการล็อกบัญชีหลังเข้าสู่ระบบผิดซ้ำนอกเหนือจากการจำกัดอัตราคำขอ
\item การดูแลโครงสร้างฐานข้อมูลต้องดำเนินการด้วยตนเอง ฐานข้อมูลที่ใช้งานจริงไม่มีประวัติ migration ของ Supabase หากสั่งนำ migration ทั้งหมดไปใช้ซ้ำจะประมวลผลไฟล์เดิมทั้งหมดอีกครั้ง จึงต้องนำไฟล์ใหม่ไปใช้ทีละไฟล์ และสคริปต์ปรับปรุงระบบ (deploy.sh) ไม่ได้ดำเนินการส่วนนี้ให้
\item ข้อมูลสถานที่จาก Google ซิงก์ได้เมื่อผู้ดูแลระบบสั่งเท่านั้น ระบบยังไม่มีการซิงก์ตามรอบเวลา และแต่ละสถานที่ที่ซิงก์ต้องเรียก Google Places API ซึ่งมีค่าใช้จ่ายตามจำนวนครั้ง จึงจำกัดชุดงานละไม่เกิน 500 แห่ง
\item แผนการเดินทางปรับแก้ไม่ได้หลังสร้างเสร็จ ระบบบันทึกทุกแผนลงตาราง trips, trip\_days และ trip\_items โดยอัตโนมัติ และผู้ใช้ที่เข้าสู่ระบบเปิดดู เปลี่ยนชื่อ ทำสำเนา และลบแผนได้ (UC-07) แต่ฟังก์ชันปรับแผนด้วยการกดถูกใจ/ไม่ถูกใจและช่องข้อเสนอแนะที่เคยพัฒนาไว้ถูกถอดออกจากหน้าผู้ใช้แล้ว ผู้ใช้ที่ต้องการแผนต่างจากเดิมจึงต้องกรอกเงื่อนไขและสร้างแผนใหม่ทั้งชุด นอกจากนี้ แผนของผู้ที่ไม่ได้เข้าสู่ระบบถูกบันทึกเพื่อสถิติของผู้ดูแลระบบเท่านั้นและเปิดดูซ้ำไม่ได้ และบัญชีหนึ่งบันทึกแผนได้ไม่เกิน 50 แผน
\item การทดสอบส่วนเว็บยังไม่เป็นระบบอัตโนมัติเต็มรูปแบบ กรณีทดสอบเชิงหน้าที่ TC-01 ถึง TC-25 รันด้วยสคริปต์แยกต่างหากบนฐานข้อมูลชั่วคราวและยังไม่รวมอยู่ในที่เก็บโค้ด Frontend ไม่มีชุดทดสอบอัตโนมัติ และ GitHub Actions ตรวจก่อนรวมโค้ดเฉพาะการสร้างโปรแกรมฝั่ง Frontend นอกจากนี้โครงงานไม่ได้ทดสอบภาระงานเมื่อมีผู้ใช้พร้อมกันจำนวนมาก การจำกัดอัตราคำขอเก็บสถานะในหน่วยความจำของกระบวนการเดียว จึงเหมาะกับการติดตั้งบนเครื่องเดียวเท่านั้น
\item ระยะทางและเวลาเดินทางในแผนเป็นค่าประมาณ ระบบคำนวณระยะทางแบบเส้นตรง (Haversine) และใช้ความเร็วเฉลี่ยคงที่ (25 กิโลเมตรต่อชั่วโมงในเขตเมือง และ 60 กิโลเมตรต่อชั่วโมงเมื่อระยะทางเกิน 15 กิโลเมตร) มิได้ใช้ข้อมูลเส้นทางหรือสภาพจราจรจริง เวลาในตารางจึงอาจคลาดเคลื่อนจากการเดินทางจริง
\item การสร้างคำอธิบายสถานที่ด้วย AI ทำได้ทีละสถานที่จากฟอร์มของผู้ดูแลระบบ หากต้องการสร้างคำอธิบายให้ทุกสถานที่ในคราวเดียวยังต้องรันสคริปต์แยกนอกระบบ
\end{enumerate}

\subsection{ข้อจำกัดด้านฮาร์ดแวร์และซอฟต์แวร์}

ระบบพึ่งพาการประมวลผลผ่านโมเดลภาษาขนาดใหญ่ตระกูล Gemini ที่เรียกผ่าน Vertex AI ของ Google Cloud ซึ่งกำหนดโควต้าอัตราคำขอต่อโครงการและคิดค่าใช้จ่ายตามปริมาณ Token ทำให้อาจเกิดการหยุดชะงักของบริการเมื่อคำขอเกินโควต้าหากมีผู้ใช้งานพร้อมกันจำนวนมาก และค่าใช้จ่ายเพิ่มขึ้นตามปริมาณการใช้งาน โดยช่วงวันที่ 10--15 ตุลาคม 2569 มีค่าใช้ Vertex AI รวม 135.24 บาท ซึ่งชำระด้วยเครดิตทดลองใช้ฟรีของ Google Cloud (ตารางที่ \ref{tab:cost}) เมื่อเครดิตหมดลงค่าใช้จ่ายส่วนนี้จะเป็นภาระของผู้ดูแลระบบโดยตรง นอกจากนี้ ค่าเกณฑ์ผ่านของกลไก LLM-as-a-Judge (0.45) ถูกปรับตั้งจากผลทดสอบกับโมเดลชุดแรกที่ใช้งาน (gemini-2.5-flash) เท่านั้น ปัจจุบันระบบเปลี่ยนมาใช้ gemini-3.8-flash และปรับขอบเขตเกณฑ์ของ Judge ให้แคบลงแล้ว แต่ค่าดังกล่าวยังไม่ได้ทดสอบและปรับเทียบใหม่

โควต้าของ LLM อาจหมดลงได้หากมีผู้ใช้งานพร้อมกันจำนวนมาก & ระบบพึ่งพาการประมวลผลผ่าน Gemini บน Vertex AI ซึ่งมีการกำหนดเกณฑ์การใช้งาน (Rate Limits) และคิดค่าใช้จ่ายตามปริมาณ Token & 1. แยกตัวแปรตั้งค่าโมเดลตามลักษณะงาน เพื่อให้เปลี่ยนโมเดลของงานใดงานหนึ่งได้โดยไม่กระทบงานอื่น และสลับผู้ให้บริการได้ด้วยตัวแปร LLM\_PROVIDER แม้ปัจจุบันทุกงานจะใช้ gemini-3.8-flash \newline 2. จำกัดจำนวนรอบการสร้างแผนซ้ำของ LLM-as-a-Judge ไว้ไม่เกินค่าที่กำหนด (MAX\_JUDGE\_ATTEMPTS) เพื่อไม่ให้คำขอเดียวใช้โควต้าเกินความจำเป็น \newline 3. ตั้งค่าให้ขั้นตอนตรวจสอบคุณภาพ (Judge) ทำงานแบบ Fail-Open หากเรียก API ไม่สำเร็จ เพื่อไม่ให้ปัญหาโควต้าที่ขั้นตอนตรวจสอบไปปิดกั้นผลลัพธ์หลักที่สร้างเสร็จแล้ว \newline 4. จำกัดจำนวนคำขอต่อผู้ใช้แต่ละราย (Rate Limiting) ที่ AI Service โดยค่าเริ่มต้นคือแชตบอต 20 ครั้งต่อนาทีและ 200 ครั้งต่อชั่วโมง ส่วนการวางแผนทริป 5 ครั้งต่อ 10 นาทีและ 20 ครั้งต่อชั่วโมง \newline 5. บันทึกปริมาณ Token และค่าใช้จ่ายโดยประมาณของแต่ละคำขอ เพื่อติดตามการใช้โควต้า \\
\hline
แชตบอตตอบช้า โดยเฉพาะคำถามต่อเนื่องตั้งแต่รอบที่ 2 และได้คะแนนความรวดเร็วในการตอบต่ำที่สุดในแบบสอบถาม (3.87) & ตั้งแต่คำถามรอบที่ 2 ระบบเรียก LLM สองครั้งต่อเนื่องกัน คือเขียนคำถามใหม่ให้เข้าใจได้ด้วยตัวเอง (Query Rewrite) แล้วจึงสร้างคำตอบ ประกอบกับ gemini-3.8-flash ใช้การคิดก่อนตอบ (Reasoning) เป็นค่าเริ่มต้นแม้กับงานสั้น ๆ ทำให้เวลารอเพิ่มขึ้นประมาณ 3--15 วินาทีอย่างไม่แน่นอน & 1. ตั้งระดับการคิด (reasoning\_effort) เป็น low เฉพาะขั้นเขียนคำถามใหม่ ลดเวลาขั้นนี้จากประมาณ 8.5 วินาทีเหลือประมาณ 3 วินาที (ขั้นสร้างคำตอบยังใช้ระดับเดิม เพราะเมื่อลดลงชุดคำถาม Golden Set ไม่ผ่าน 10 จาก 33 ข้อ) \newline 2. ส่งคำตอบแบบทยอยแสดงผล (Streaming) ให้ผู้ใช้เห็นข้อความก่อนคำตอบเสร็จ \newline 3. กำหนดเวลารอ LLM ขั้นเขียนคำถามใหม่ 8 วินาที (เกินแล้วใช้คำถามเดิม) และขั้นสร้างคำตอบ 25 วินาที ลองซ้ำได้ 1 ครั้ง \\
\hline
การสร้างแผนการเดินทางใช้เวลานาน ผู้ใช้ให้คะแนนความรวดเร็วในการสร้างแผนเที่ยว 3.90 และคะแนนข้อนี้กระจายมากที่สุด (S.D. 1.25) & การสร้างแผนต้องเรียก LLM หลายขั้นต่อกัน ได้แก่ การคัดเลือกสถานที่ ซึ่งในการทดลอง Prompt ด้วยโมเดลจริงใช้เวลาเฉลี่ยประมาณ 27.5 วินาทีต่อครั้งสำหรับ Prompt ที่ใช้งานจริง ตามด้วยการตรวจคุณภาพของ Judge และหากแผนไม่ผ่านต้องคัดเลือกใหม่อีกรอบ อีกทั้งไม่สามารถทยอยแสดงผลได้ เพราะตัวจัดตารางต้องได้ผลลัพธ์ JSON ครบทั้งชุดก่อนจึงจัดลำดับและคำนวณเวลาได้ & 1. จำกัดวงรอบสร้างแผนและตรวจคุณภาพไว้ไม่เกิน 2 รอบ (MAX\_JUDGE\_ATTEMPTS) \newline 2. กำหนดเวลารอ LLM ไว้ 120 วินาทีสำหรับการคัดเลือกสถานที่ และ 60 วินาทีสำหรับ Judge โดยปิดการลองซ้ำอัตโนมัติของไลบรารี เพื่อไม่ให้คำขอที่ค้างทำให้ผู้ใช้รอที่หน้ากำลังโหลดเป็นเวลานาน \newline 3. ให้ Judge ทำงานแบบ Fail-Open หากเรียก API ไม่สำเร็จ ระบบส่งแผนที่สร้างเสร็จแล้วกลับไปโดยไม่รอการตรวจ \newline 4. ให้ LLM คืนเฉพาะรหัสสถานที่ของแต่ละวัน ส่วนการจัดลำดับและคำนวณเวลาทำด้วยโค้ดเชิงกำหนดแน่นอน \newline 5. ยังไม่ได้วัดเวลาสร้างแผนทั้งกระบวนการในการใช้งานจริง (ดูหัวข้อข้อเสนอแนะ) \\

\subsection{การปรับปรุงฟังก์ชันการทำงาน}

เพื่อให้ระบบมีความสมบูรณ์และพร้อมใช้งานจริงยิ่งขึ้น ควรเสริมมาตรการความปลอดภัยของเว็บแอปพลิเคชันที่ยังเปิดอยู่ ได้แก่ การกำหนด Content Security Policy การตรวจชนิดไฟล์อัปโหลดจากเนื้อไฟล์ และการล็อกบัญชีหลังเข้าสู่ระบบผิดซ้ำ ควรจัดให้ฐานข้อมูลที่ใช้งานจริงมีประวัติ migration เพื่อปรับปรุงโครงสร้างได้อัตโนมัติ และเพิ่มการซิงก์ข้อมูลสถานที่ตามรอบเวลา ควรนำกรณีทดสอบเชิงหน้าที่ของส่วนเว็บเข้าไว้ในชุดทดสอบอัตโนมัติของที่เก็บโค้ดและรันใน GitHub Actions ทดสอบฟรอนต์เอนด์ และทดสอบภาระงานเมื่อมีผู้ใช้พร้อมกันจำนวนมาก ควรพัฒนาช่องทางให้ผู้ใช้ปรับแผนการเดินทางหลังสร้างเสร็จ โดยส่งความเห็นของผู้ใช้กลับไปให้ระบบวางแผนประมวลผล นอกจากนี้ ควรศึกษาแนวทางการเข้าถึงข้อมูลความหนาแน่นของผู้คนจากแหล่งข้อมูลเปิดอื่นที่ยังไม่เคยทดลอง เพื่อเพิ่มประสิทธิภาพในการแนะนำแผนการเดินทางให้สอดคล้องกับสถานการณ์จริงยิ่งขึ้นและเมื่อฟังก์ชันหลักครบถ้วนสมบูรณ์ ควรทดสอบยอมรับจากผู้ใช้แบบกำหนดภารกิจ (UAT) และเก็บแบบสอบถามความพึงพอใจจากกลุ่มผู้ใช้ที่กว้างและหลากหลายกว่าเดิม เพื่อประเมินประสิทธิภาพและความพึงพอใจของผู้ใช้งาน รวมถึงปรับเทียบค่าเกณฑ์ผ่านของกลไก LLM-as-a-Judge ใหม่ให้ตรงกับโมเดลที่ใช้งานอยู่ ทดลองระบบวางแผนการเดินทางแบบรวมวงรอบสร้างแผนใหม่ของ Judge และประเมินแชตบอตตามตัวชี้วัด Answer Relevance, Faithfulness และ Context Recall/Precision ที่วางแผนไว้ ตลอดจนเปรียบเทียบโมเดลภาษาขนาดใหญ่หลายรุ่นในด้านความแม่นยำ ความเร็วในการตอบสนอง และต้นทุนการใช้งาน เพื่อเลือกโมเดลที่เหมาะสมกับแต่ละฟังก์ชัน (แชตบอต, Trip Planner, Judge) แทนการใช้ gemini-3.8-flash รุ่นเดียวกับทุกฟังก์ชันดังในปัจจุบัน

\subsection{แนวทางการวิจัยต่อยอด}

นอกจากการปรับปรุงฟังก์ชันข้างต้น ผลของโครงงานนี้ชี้ให้เห็นประเด็นที่ควรศึกษาต่อยอดในเชิงวิจัย ได้แก่ การตรวจสอบความน่าเชื่อถือของการประเมินด้วย LLM โดยเทียบคะแนนของ LLM-as-a-Judge และผู้ประเมิน LLM ในการทดลองกับคะแนนจากผู้ประเมินที่เป็นมนุษย์ ซึ่งการทดลองในบทที่ 4 พบว่าผู้ประเมิน LLM ทั้งสามตัวให้คะแนนรายรันไม่สอดคล้องกัน การนำข้อมูลเส้นทางและสภาพการจราจรจริงมาใช้ในตัวจัดตารางแทนการประมาณระยะทางแบบเส้นตรง เพื่อให้ตารางเวลาในแผนเป็นไปได้จริงมากขึ้น ซึ่งเป็นข้อที่ผู้ใช้ให้คะแนนต่ำในแบบสอบถาม และการวัดผลของระบบต่อการวางแผนท่องเที่ยวจริง เช่น เวลาที่ผู้ใช้ใช้วางแผนเมื่อเทียบกับวิธีเดิม เนื่องจากผลในโครงงานนี้เป็นความเห็นของผู้ใช้ มิใช่ค่าที่วัดจากการใช้งานจริง
